### Runs 25-26: the matched A/B, and a claim it contradicts

**Instrument.** Runs 26A/26B are the discharge the review round 13 OPEN ITEM asked for: one quiet box, both
probe-stop variants, back to back in a single 6-minute window, with review-tool contention SAMPLED every
5 s throughout rather than assumed. All 118 busy samples fall in the 10-minute WAIT phase that
preceded the pair; both measurement windows are clean. Run 25 is retained as a FAILED instrument
(contended mid-run) and is **not** load-bearing for anything below. Machine profile now recorded
above.

**The measured A/B (DEMONSTRATED, max ms per arm):**

| arm | 26A act-derived | 26B constant | delta |
|---|---|---|---|
| mixed / no pending | 293.17 | **201.04** | −92.13 |
| mixed / pending | 353.58 | **267.05** | −86.53 |
| send-authorizer / no pending | 227.95 | **182.51** | −45.44 |
| send-authorizer / pending | 270.08 | **231.05** | −39.03 |

The CONSTANT stop is faster on **every** arm, by 39-92 ms — far outside this box's documented
±45 ms drift band on the two larger deltas. Under it, 3 of 4 arms PASS and the gate's only
remaining failure (mixed/pending) misses by **17.1 ms**, which is INSIDE the drift band.

**⚠ THIS CONTRADICTS A LOAD-BEARING CLAIM IN THE CODE.** `crates/aruna/src/store_open.rs:479-486`
justifies review round 13's restoration of the act-derived stop with: *"Measured at run 23 …, the constant's
O(min(active, 8193)) scan per probe per firing FAILED the 250ms gate outright (353.8ms
mixed/pending) … So the stop is act-derived again."* Today's clean pair measures the constant at
**267.05**, while the **act-derived** form reproduces run 23's 353.78 to within **0.2 ms**.

**What is and is not claimed:**
- **DEMONSTRATED:** in one clean matched window, constant beats act-derived on all four arms.
- **NOT CLAIMED — that run 23 was mislabeled.** Run 23 was taken on an *uncommitted working tree*
  ("d8922db + the uncommitted review round 13 fix"), and `bb23fed` is the commit that introduced the
  act-derived assignment (`git log -S`, verified). The bytes behind run 23 are therefore
  **unrecoverable**, and two readings stay open: (a) run 23 already carried the act-derived
  restoration, or (b) that evening's box sat ~87 ms high — nearly 2× the documented drift band.
  This is why an uncommitted-tree measurement cannot settle a perf attribution.
- **NOT CLAIMED — that the constant stop is correct.** 26B is a throwaway probe edit, reverted at
  the byte (revert verified in-script). Its behavioural witnesses
  (`the_limit_bounded_activation_probes_agree_with_the_unbounded_form`, `codex_r6_f1_*`) were green
  in the review round 8-12 era but were **NOT re-run** under today's variant. Reverting review round 13's fix is a CODE
  decision with a stated correctness rationale and is not a measurement-only change.

**Adjudication, against the pre-committed branches:** not a PASS (267.05 > 250 on the constant);
not a FAIL by real margin (17.1 ms sits inside ±45 ms). This is the **BORDERLINE** branch — *the
box is not an instrument at this bound* — so the pinned-profile question rides into the design
round regardless, exactly as the discharge specified.

**What this buys the validated-at-write design draft:** its perf hypothesis — that deleting per-firing JSON
removes the dominant recurring cost — now has its **first clean empirical support, and it is
directional only**: 26B removes ONE of the trigger's two per-firing JSON sites (the probe-limit
derivation) and bought 39-92 ms, while the domain-guard JSON in the comparison arm remained in
both variants. The validated-at-write close deletes *all* of them; that remains a HYPOTHESIS, and
the hypothesis stays PENDING until the build measures it.

### ⚠ RUN 27 — VOID, and the process finding it produced

During a design review, a reviewer executed the real `PHOTON_PERF=1` gate. It regenerated this
file's machine sections in place (table + commit SHA + machine profile), overwriting the run-26A
values and the hand-filled CPU field. **The FULL RECORD tail survived** — the record-preserving
writer worked as designed.

**The run is VOID and its numbers are deliberately NOT recorded as evidence.** It executed while
three reviewers were concurrently reading, grepping, compiling and probing this repo — the exact
multi-tenant contention that made run 25 a failed instrument, and with no contention sampling at
all. For the record only, discarded: mixed/no 311.2 · mixed/yes 383.2 · send-auth/no 256.2 ·
send-auth/yes 264.4 (all four over). Directionally consistent with heavy contention; evidentially
worthless. This file was restored to its previous committed state.

**Process finding — the benchmark is not safe for a read-only reviewer to execute.**
`crates/aruna/tests/capacity_seize_bound.rs:770` WRITES this repository file as a side effect of
running, so executing it exceeds a read-only reviewer's authority by construction. A reviewer who
attempted it hit a tool timeout and honestly reported no independent latency result — but the write
had already landed. The lesson: *a timed-out probe still has side effects; "no result" is not
evidence that nothing happened.*

**Residual for the build:** the evidence writer should be gated behind an explicit opt-in (or write
to a temp path unless asked), so that running the gate is observation, not mutation. Until then, a
read-only reviewer should not be asked to execute this benchmark.
