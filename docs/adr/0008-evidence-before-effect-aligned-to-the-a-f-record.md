# ADR-P008: Evidence-before-effect, aligned to the A–F record

**Status:** Accepted


> **Revised after review.** This section's original mechanism prose ("signed local records, linear hash
> chain, append-only") described building a second evidence custodian. The mechanism is recut as a
> **producer profile of one shared evidence-anchor primitive**: a sibling surface's anchor has no
> independent tree, chain, key, or store. Nothing was built against the old prose — Photon's production
> crypto surface was zero — so this is a pre-build correction at prose cost. The **intent paragraph is
> unchanged**: evidence-before-effect, fail-closed, A–F shape, a drop-in custodian.

**Decision.** Photon writes evidence as the A–F record (consent / authority+bounds / who-acted / what-was-shown / seizure-substance where applicable / signed proof-of-authority-at-instant), written and authenticated AS the transition, BEFORE the effect commits. The authentication grain depends on the per-row-signature-versus-keyed-MAC decision below (per-row signature under option A; keyed MAC with a checkpoint-bound asymmetric signature under option B); the invariant restatement at Layer 0 governs, and it is an explicit revision of the original unconditional "signed", never a silent weakening. **If the evidence write fails, the action MUST NOT proceed** — with one carve-out, adopted here AS THE COMPLETE CONTRACT: **unilateral human seizure/kill is SEVER-FIRST, audit best-effort AFTER.** (1) The sever (epoch bump / kill) commits depending on **NOTHING** audit-related — no evidence append, no normalization or metadata/size check, no sink access, and no inspection or serialization of any caller-supplied object whose reflection or coercion could throw, hang, or side-effect. (2) The seizure substance is logged best-effort, AFTER the sever, on an isolated lane; a failing, hung, hostile, or malformed post-sever audit is a **flagged fault for reconciliation, never a blocked sever and never a silent erasure**. (3) What the seizure claims survives a lost audit because it is committed in a **durable Sever-Commit Witness atomic with the sever itself** (not with the append). The witness payload is defined: at minimum the post-sever epoch, the sever timestamp, the seizing-authority reference (by reference, never PII substance), and the claimed count and digest over the affected in-flight intent set; a witness carrying only the epoch bump loses the authority and abort claims this contract exists to preserve. The witness PROPERTIES: construction is **content-blind and bounded** — the sever path never enumerates, serializes, or touches intent content or caller objects at kill time, and the digest is never a bare digest over mailbox-bearing data — and the witness is **truthful**: its claimed affected set matches what the seizure actually affected, neither counting an action that lawfully completed (false abort evidence — the audit-trail-lying defect ADR-P013 forbids in both directions) nor omitting one the kill actually caught. The accumulator/membership protocol that delivers these properties (admission and terminal boundaries, the race-winner predicate, loser inclusion) is a design decision for the evidence-spine slice. (4) **Honest scope:** this is the seize's OWN-path independence, NOT a bounded-kill-latency guarantee — Photon's engine is `execute(&mut self)`-serialized, so an in-flight machine transition holding the executor with a hung PRE-COMMIT append can DELAY an in-process kill verb; the structural close (a kill-preemptible execute lock) is bound to ADR-P013's deferred concurrency item (a), and until it lands the process-level kill (killing Photon itself) is the lever no lock can block. Evidence-before-effect governs the machine's actions, not the human's kill: the bigger lever is never harder to reach. The legacy audit/diagnostic JSONL separation (inherited from the Agent-MailOps seed) graduates to the A–F schema rather than being replaced.

**Mechanism (four layers — Photon is a PRODUCER, not a second custodian).** When Photon's evidence spine is built (build-order item 5), it instantiates a shared evidence-anchor contract as a **producer profile**, never an independent implementation. Standalone Photon hosts the local-tier component (local driver, local notary); Photon owns only A–F record construction and the producer/append seam. Format compatibility is never license for a compatible reimplementation. Every layer names its adoption target, because "adopted, never authored" without a named source is an aspiration:

- **Layer 0 — chain (write-path spine):** every evidence row gains seal fields — **sequence + prev-hash + per-row authentication material**; single-writer, notary-enforced ingest with an append credential **independent of every agent/tool credential**. ⚠ **Granularity is a deferred decision:** whether the per-row material is an asymmetric signature (option A) or a keyed MAC whose asymmetric binding lands at the checkpoint/root (option B, batch-sign) is a capacity call against a measured append-rate budget; this ADR adopts whichever is chosen and prejudges neither. **Invariant restatement:** under option A, "signed-before-effect" holds literally at row grain. Under option B the invariant reads **authenticated-and-durably-notarized before effect**: the row's keyed MAC plus the notary's durable acknowledgment gate COMMIT, and the asymmetric, publicly verifiable binding lands with the signed checkpoint at a **bounded checkpoint cadence that is distinct from — and at or after — the COMMIT release point**. Conflating the two either forces checkpoint-per-COMMIT, defeating option B, or overclaims proof at release. The row-to-signed-checkpoint window is the standalone tier's unanchored tail (honesty note below), and the item-5 slice must name and bound that cadence. Bounded means **fail-closed**: the tail has a maximum age and size, and an overdue or failed checkpoint eventually blocks further COMMITs rather than growing an indefinitely unsigned tail (idle traffic still flushes; a dead signer stops the line). Requiring a signed checkpoint before every COMMIT would force option A's cost profile and prejudge the deferral. ⚠ The implementation-level seal schema is **owed, not yet written**; if it has not landed when build-order item 5 opens, that is a **blocking dependency** of the slice — never a license to author a chain schema here. The schema alone is not the dependency: item 5 consumes a named, versioned shared local-tier component for the notary/chain/CAS/checkpoint mechanics, and if no consumable shared component exists when item 5 opens, that too is blocking, because implementing those mechanics locally would be the independent implementation this ADR forbids.
- **Layer 1 — tree:** the RFC 6962 §2.1 Merkle-tree construction (RFC 6962 is Experimental and obsoleted by RFC 9162 as the CT protocol; its tree construction remains the live transparency-log baseline because the adopted checkpoint spec names it), via a maintained tlog library (Tessera-class; no bespoke history tree); library selection is a build-ticket row. SHA-256 *inside* the tree is compelled by the adopted format, not chosen — forking the tree to SHA-384 would break format compatibility.
- **Layer 2 — checkpoint:** C2SP `tlog-checkpoint` at the exact namespaced tag **`tlog-checkpoint/v1.0.0`** (C2SP tags are `<spec>/vX.Y.Z` — a bare "v1.0.0" is ambiguous across the repo's specs; a later tag may be adopted only through gate (e)'s re-verification). The pinned spec is adopted **with all its normative requirements** (non-empty origin; extension lines are optional and not recommended at the tag, and only those actually present must be non-empty; clients must ignore unknown signatures; and the safety-bearing one is consistency: *"Logs MUST not sign any checkpoint which is inconsistent with any checkpoint it previously signed."*), **narrowed by a stricter profile that governs:** origin = `mw/<tenant_id>/<vault_id>` (opaque IDs, no PII-looking components) · **extension lines prohibited** (witnessed semantics go into the tree as rows or the sidecar bundle, never extensions) · the FIPS-module signature is a second note signature on the same checkpoint, a named profile decision — never a format extension.
- **CAS (storage seam, alongside Layer 0):** artifacts land in a content-addressed store named by **SHA-384** — the CAS address is a bare digest by design ("identity is the address"). ⚠ **Governed-content composition rule:** where a CAS object contains governed content (e.g. a full RFC-822 snapshot), its bare address stays sink-internal ("never travels, dies with the object") — the durable evidence row's reference to such an object is opaque or commitment-bound, never the bare content digest; otherwise the row would carry a publicly recomputable equality oracle over governed content into the log, violating the commitment rule below. Non-governed artifacts reference by bare CAS address as designed.
- **Layer 3 — signature suite: not selected here, and multi-leg by design.** The profile is **role-preserving, never single-suite**: Ed25519 stays the public-witness-network compatibility leg; ECDSA P-384/SHA-384 stays the FIPS 186-5 ladder leg; pure ML-DSA-87 (FIPS 204) is the additive CNSA leg; HashML-DSA is prohibited, authenticated suite descriptors and downgrade rejection are required (carrier `mw.seal-signature-suite.v1`), and ML-DSA-87 may never erase the compatibility/FIPS legs. Facts decided on this page so a builder cannot inherit them silently: (a) the adopted checkpoint spec at its stable tag recommends **Ed25519** (an ML-DSA-44 recommendation exists only in later, unadopted cosignature material — editor copies and a tagged release candidate (`tlog-cosignature/v1.1.0-rc.1`) — never treat unadopted content as a default); (b) **ML-DSA-44 is not CNSA-profile-conformant, at any tag, present or future**; (c) the item-5 suite decision selects the required legs for the deployment per the role matrix — it never collapses the profile to one algorithm and never inherits a default from either source silently. The Ed25519 floor is conditioned on public-witness-network interaction, so the standalone tier's leg set is a gate-(c) decision, never an inherited SHOULD.
- **Content-derived integrity values (scoped):** durable, content-derived integrity slots for governed content in Photon's own records use a keyed commitment, `mw.commitment.v1`: HMAC-SHA-384, full 384-bit tag, independent keys (no derivation), and a `key_ref` (tenant/namespace × epoch) inside the authenticated preimage — omitting it re-opens the tag-reassociation class that `key_ref` closes. **Exclusions (each a different digest domain):** CAS object addresses · sealed-row/event-byte digests · Merkle/checkpoint values · externally mandated digests · provenance identifiers and idempotency keys (provenance-keyed, never content-keyed) · provenance/attestation bindings (e.g. the existing drill-lane helper-source/token digests). **Honest limits:** the commitment is key-holder-verifiable only — not publicly verifiable. **Public-proof composition** (conditional on the per-row authentication option chosen — stated so no builder under-claims or over-claims): the CAS address is publicly recomputable in every branch; under option A the row signature verifies publicly; under option B the row MAC is key-authority-checkable only, and the public binding of row bytes into history is the inclusion proof plus the signed checkpoint/root. In both branches, proof that a row entered the committed history requires a **Merkle inclusion proof + a signed checkpoint** (and a consistency proof / witnessed lineage where the tier claims historical continuity); verification is recomputation, O(log n). A commitment enters an evidence slot only with its key-holder-only limit named.
- **Standalone posture:** until Photon attaches to a governed deployment, the local-tier component is instantiated locally — same component, same shapes, same formats, so a deployment's evidence custodian remains a **drop-in**. Photon never forks the ingest rule, tree, or checkpoint format. ⚠ **The standalone→deployment attach transition is deliberately undefined here** (whether locally-emitted history — key, chain genesis, sequence, checkpoint lineage — is adopted into the deployment's log, migrated, or epoch-cut at attach). The binding rule and its gate live in **build-order item 5's acceptance criteria**: an adoption/migration/epoch-boundary rule MUST exist **before any standalone evidence is emitted**. Until then, "drop-in custodian" is a format-compatibility claim, not a history-adoption claim.

(Honesty note: software alone delivers append-only + hash-chain + access control. True "nothing can come out" non-exfiltration is data-diode territory — a hardware/architecture decision for the custodian itself, out of Photon's scope. **The standalone local tier carries an integrity ceiling, imported with the mechanism:** detection-capable, not breach-survivable; no forward security under a static notary key (a key-thief admin can rewrite pre-compromise rows into a clean, validly-signed chain); no equivocation/split-view defense without a witness; the unanchored tail is irreducible on a single host. Code already running on the user's machine with the user's privileges is out of scope; the witnessed tier at deployment attach is the cure, never an on-box wall. Photon's obligation is to write evidence *to the profile* so custody can harden without Photon changing.)

**Why.** Traceability is the product. "Everything is logged, risky things are backed up, any action is traceable" is the entire enterprise and regulatory story, and it only holds if evidence is structurally prior to effect — an after-the-fact log is a diary, not evidence.

**Rejected.** Best-effort logging with retries (fail-open is fail); a bespoke mail evidence schema (two surfaces, one contract — see ADR-P004).
